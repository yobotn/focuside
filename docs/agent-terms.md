# Spawn the vendor's agent, never its login

FocusIDE can support every agent on its list within the vendor's terms if it follows one rule: start the user's own, unmodified agent binary, let the agent run its own login, and never hold, read or pass on a token. For most vendors that rule is enough on its own. ACP chat mode is a documented or tolerated path for Codex, Antigravity CLI, Gemini CLI, Copilot CLI, Cursor, Kiro and every open source agent on the list. Claude is the exception, and the reason is billing, not technology. For Claude, the only written permission that covers a subscription login is the sentence that says Anthropic does not prevent "an end user from signing in to the unmodified Claude Code binary with their own Claude subscription". So **subscription users should get pane mode (the real `claude` TUI in a PTY), and API key and cloud provider users keep chat mode**. The adversarial check found three problems that change the Claude plan. First, FocusIDE already falls under Anthropic's Commercial Terms because its installer ships the `claude-agent-acp` executable, and that executable embeds the proprietary Agent SDK. Second, the current hard block on subscription logins conflicts with the clause that bars restricting "any authentication method built into" Claude Code. Third, Anthropic runs a content classifier that has hit traffic from the real binary, so pane mode must stay observe-only and human-driven. The work needed is moderate: extract a shared turn recorder from `session.rs`, add a session kind for agent panes, stop bundling the adapter (or document it properly), fix stale launch flags, and rewrite the copy that says Claude plans cannot be used. Stopping the bundle ends redistribution, but it does not end the Commercial Terms question for chat mode, because FocusIDE still uses the SDK to power its product. A second challenge round found that the hook design needs stricter rules than the first draft gave: some hook output goes straight into the model's context, a project-scope plugin install writes into the user's repo, and a plugin in a separate repo cannot find FocusIDE's helper on every OS. Those fixes are in the hook sections and in "Second challenge: what changed". This is not legal advice.

## One rule covers six vendors, and Claude needs a second front end

The two front ends carry different risk because they look different to a vendor. In **chat mode**, FocusIDE's own UI sends prompts over ACP to an agent process. That is a third-party client driving the agent through a programmatic interface. In **pane mode**, the vendor's own TUI runs in a PTY, the user types every prompt, and FocusIDE only watches the disk and receives hook events. That is the vendor's own front end, used by a human, which is the pattern that vendor terms protect most clearly. JetBrains Air already draws exactly this line for Claude. Its docs say "A Claude subscription cannot be used to authorize Claude Agent in the chat surface" and "To use your Claude subscription, run Claude Code in the terminal surface" ([JetBrains Air](https://www.jetbrains.com/help/air/air-in-ides-authorization.html)) **[Confirmed]**. Zed takes a looser line and lets plan users run `/login` inside its ACP thread ([Zed external agents](https://zed.dev/docs/ai/external-agents)) **[Corrected: the first round said Zed sends subscription users to the terminal; that advice was only in a blog post about the paused billing split]**.

Most vendors invite chat-mode clients in writing. GitHub lists "Custom frontends" as an intended use of `copilot --acp` ([GitHub changelog, 2026-01-28](https://github.blog/changelog/2026-01-28-acp-support-in-copilot-cli-is-now-in-public-preview/)) **[Confirmed]**. Cursor says "ACP is intended for building custom clients and integrations" ([Cursor ACP](https://cursor.com/docs/cli/acp)) **[Confirmed]**. Kiro says "Any editor supporting ACP can integrate Kiro by spawning `kiro-cli acp`" ([Kiro ACP](https://kiro.dev/docs/cli/acp/)) **[Confirmed]**. Google says "Any ACP client can launch Antigravity CLI" ([Antigravity ACP](https://antigravity.google/docs/ide/extensions/acp/)) **[Confirmed]**. OpenAI describes Codex app-server, which `codex-acp` now sits on, as the surface for "a deep integration inside your own product" ([Codex app-server](https://learn.chatgpt.com/docs/app-server)) **[Confirmed]**. What every vendor forbids is the opposite pattern: third-party code that takes the agent's OAuth token and calls the vendor's backend directly. Google calls it a violation to "harvest or piggyback on Gemini CLI's OAuth authentication" ([Gemini CLI FAQ](https://geminicli.com/docs/resources/faq/)) **[Confirmed]**. Anthropic says developers "may not collect, store, or intermediate Claude.ai credentials or session tokens" ([Claude Code legal](https://code.claude.com/docs/en/legal-and-compliance)) **[Confirmed]**. FocusIDE's credential rule (`PLAN.md:135`, `AGENTS.md`) already keeps it out of that pattern.

The owner's rule also removes one option on purpose. OpenAI's "Sign in with ChatGPT" (SIWC) program does allow open source apps to use a ChatGPT plan: "At launch, ChatGPT plan usage is available to open-source projects, personal projects that run locally, and selected private apps" ([OpenAI Cookbook](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt)) **[Confirmed]**. But the app must "store the user's basic account info and credentials" and pass `ACCESS_TOKEN` to the Codex app-server child ([SIWC token sharing](https://developers.openai.com/siwc/token-sharing-open-source), [SIWC app-server](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)) **[Confirmed]**. That breaks "never reads, stores or proxies credentials", so this report excludes SIWC. FocusIDE uses Codex's own login instead.

## Claude: pane mode is the only written path for plans, and ACP mode already sits under Commercial Terms

### What Anthropic's text allows and forbids

Anthropic's legal page sets three rules that matter here, all **[Confirmed]** on the live page ([Claude Code legal](https://code.claude.com/docs/en/legal-and-compliance)). Developers "including those using the Agent SDK, should use API key authentication", and Anthropic "does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users". The carve-out says the rules do not "prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription". And "preinstalling or running Claude Code in your products or services ... requires agreeing to our Commercial Terms of Service", with conditions: the binary "must not be modified", customers "may not remove, disable, or restrict any authentication method built into it", and they "may not pay for, resell, or intermediate Claude usage". The Agent SDK page adds: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK" ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)) **[Confirmed]**.

The page does not say whether a free GPL desktop app counts as "your products or services" **[Corrected: the first round treated the clause as aimed at hosting businesses only]**. The example ("hosted sandboxes or other agent infrastructure") points at hosts, but "running Claude Code in your products" is a plain-text fit for pane mode. The safe course is to treat the conditions as binding on FocusIDE: unmodified binary, every login method left available, no paying for usage **[Inference]**.

### Three Commercial Terms problems the first round missed

**FocusIDE already distributes Anthropic code.** The challenge round found that the adapter release is built with `bun build --compile` and embeds `@anthropic-ai/claude-agent-sdk` ([claude-agent-acp repo](https://github.com/agentclientprotocol/claude-agent-acp)) **[Confirmed]**. The SDK license reads "(c) Anthropic PBC. All rights reserved. Use is subject to Anthropic's Commercial Terms of Service" ([Agent SDK LICENSE](https://raw.githubusercontent.com/anthropics/claude-agent-sdk-typescript/main/LICENSE.md)) **[Confirmed]**, and the SDK page says its use "is governed by Anthropic's Commercial Terms of Service, including when you use it to power products and services that you make available to your own customers and end users" ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)) **[Confirmed]**. FocusIDE ships that 113 MB executable as a Tauri sidecar (`apps/desktop/src-tauri/tauri.bundle.conf.json:4`, `scripts/fetch-adapter.mjs:10-39`). So chat mode is under Commercial Terms whatever the answer for pane mode. The README line "FocusIDE works with these agents. It does not include them" (`README.md:204`) is not accurate today.

**The subscription block conflicts with "may not ... restrict any authentication method".** Today `Session::start` runs `claude auth status --json` and aborts on a plan login (`apps/desktop/src-tauri/src/session.rs:136-148`, `crates/core/src/agent.rs:99-133`). Read literally, that restricts a login method built into the binary as FocusIDE runs it **[Corrected: new finding in the challenge round]**. The way out is to stop blocking and start routing. The binary's login is never touched in pane mode. Chat mode is the Agent SDK product, and the SDK note asks third parties not to offer claude.ai login there. So FocusIDE should send plan users to pane mode, with all of the binary's login methods intact, rather than refuse them **[Inference]**. This reading should be confirmed in writing.

**The adapter can offer claude.ai login inside FocusIDE's UI.** Without flags, the adapter advertises an ACP auth method "Claude Subscription" (args `--cli auth login --claudeai`). With `--hide-claude-auth`, "the agent hides the claude.ai login method from `initialize`, and refuses with `authRequired` every session and every turn that a subscription would pay for" ([claude-agent-acp `src/hide-claude-auth.ts`](https://github.com/agentclientprotocol/claude-agent-acp/blob/main/src/hide-claude-auth.ts)) **[Confirmed in source; the README does not mention the flag]**. The module's own summary is "this integration must never bill a claude.ai subscription". FocusIDE parses `authMethods` (`crates/core/src/acp.rs:309,322`) but does not show them. If it showed the default list, it would be "offering Claude.ai login" in its own UI, which the SDK page bars without prior approval. Passing `--hide-claude-auth` in chat mode moves the billing guard into the upstream adapter, which was built for this exact purpose **[Inference]**. Two limits in the source mean FocusIDE should still keep its own `claude auth status` check before start, for routing: the per-prompt account check "is not awaited, so a credential swapped after it ran stays unseen until the next prompt", and "The `/remote-control` command that the adapter runs is not guarded" ([`src/v2/subscription-guard.ts`](https://github.com/agentclientprotocol/claude-agent-acp/blob/main/src/v2/subscription-guard.ts)) **[Confirmed in source]**.

There is a better middle path than either a silent block or the full list. With the flag on, the adapter still advertises the "Anthropic Console" terminal method (`--cli auth login --console`, "API usage billing") ([`src/auth-methods.ts`](https://github.com/agentclientprotocol/claude-agent-acp/blob/main/src/auth-methods.ts)) **[Confirmed in source]**. FocusIDE can show the methods the adapter advertises under the flag and run the chosen one in a terminal pane. That is the binary's own login flow, so FocusIDE never sees a token. Next to that list, a plan user sees "Open Claude in a pane", which keeps every built-in login method reachable through the product. Whether the flag still counts as "restricting" a login method is an open question for Anthropic, because inside the chat surface it has the same effect as the current block.

### Hook data that pane mode needs

The hook payloads FocusIDE needs are documented **[Confirmed]** ([Hooks](https://code.claude.com/docs/en/hooks)). `UserPromptSubmit` carries `prompt` and `session_id` and marks turn start. `Stop` carries `last_assistant_message` and marks turn end; it "Does not run if the stoppage occurred due to a user interrupt", so an interrupt has to be inferred from the next `UserPromptSubmit` or closed by the Checkpoint button. API errors do not fire `Stop` either: "API errors fire StopFailure instead", so the plugin also listens to `StopFailure` and closes the turn there **[Confirmed]**. `PreToolUse` and `PostToolUse` give tool names, file paths and shell commands, which replace the ACP `edits` and `commands` that the "outside this session" flag and the undo dialog need (`session.rs:329-389`, `turns.rs:30-35`).

Plan capture is documented, not only plausible **[Confirmed in docs; corrected from Inference; still untested]**. For `ExitPlanMode`, "Claude Code injects the plan content and file path before passing the input to hooks", as `tool_input.plan` and `tool_input.planFilePath`. In `PostToolUse`, "`tool_response` is an object with `plan` and `filePath` fields holding the approved plan". So the plan card takes the proposed plan from `PreToolUse` and marks it approved on `PostToolUse`. The first draft said the start snapshot for a planned turn is taken when `ExitPlanMode` fires. That is not needed: in the TUI, approval continues the same turn, plan mode makes no edits, and the snapshot taken at `UserPromptSubmit` is already the right base.

### Hook delivery and transport

The first draft left two gaps here. The architecture notes say FocusIDE has no IPC besides the single-instance argv forward (`apps/desktop/src-tauri/src/lib.rs:58-66`). File drops into app data fit that, because the helper only needs to append to a file and FocusIDE's watcher only needs a second root. The env var reaches the helper, since hooks inherit Claude Code's environment and Claude Code inherits the PTY child environment **[Confirmed]**. The app data path is resolved by FocusIDE and passed in full, so the helper never has to know the OS layout.

The harder gap is finding the helper. A plugin in a separate repo cannot know where FocusIDE installed its sidecar. Shell form such as `"$FOCUSIDE_HOOK"` does not work everywhere: hooks default to bash, "or to `powershell` on Windows when Git Bash isn't installed", and the two shells expand variables differently. Exec form (`args` present) avoids shell quoting and works with paths that contain spaces, but it only substitutes path placeholders such as `${CLAUDE_PLUGIN_ROOT}`, and "On Windows, exec form needs a real executable" ([Hooks](https://code.claude.com/docs/en/hooks)) **[Confirmed]**. Two delivery options solve this:

| Option | How | Pros | Cons |
| --- | --- | --- | --- |
| A. `--plugin-dir` (suggested) | FocusIDE writes the plugin folder for the current OS into app data, with `hooks/hooks.json` in exec form pointing at `${CLAUDE_PLUGIN_ROOT}/bin/focuside-hook(.exe)`, and starts its panes with `claude --plugin-dir <that folder>`. The flag loads a plugin "for this session only" ([CLI reference](https://code.claude.com/docs/en/cli-reference)) | Hooks run only in panes FocusIDE starts; nothing in `~/.claude`; plugin and app versions always match; no marketplace | FocusIDE adds a launch flag, so it needs a one-time consent prompt; whether managed policy can block `--plugin-dir` was not checked **[Unverified]** |
| B. Marketplace install by the user | The plugin repo ships per-OS helper binaries; `hooks.json` cannot pick a per-OS command, so it needs a tiny launcher per OS or a binary with the same name on every OS | Most explicit consent | Hooks fire in every Claude session on the machine (the helper exits early when `FOCUSIDE_EVENTS` is missing); auto-update off by default; a binary in a git repo |

Do not use `--settings` for this. Its values "override the same keys in your `settings.json` files for this session" ([CLI reference](https://code.claude.com/docs/en/cli-reference)), so passing a `hooks` key could hide the user's own hooks **[Inference from the doc text]**. HTTP hooks were also considered and rejected: the URL cannot take an env var (interpolation works only in headers), so a fixed local port would be needed, and a closed port shows a hook error in the transcript of every non-FocusIDE session.

## The claude-agent-acp license: Apache source, proprietary payload

Both labels are real, and they describe different things **[Corrected: the first round called the adapter Apache-2.0 and safe to ship beside GPL code]**. The repo's LICENSE is Apache 2.0 ("Copyright 2025 Zed Industries, Inc. and contributors") and `package.json` says `"license": "Apache-2.0"`, but the registry entry `claude-acp` says `"license": "proprietary"` with authors Anthropic, Zed Industries and JetBrains ([registry.json](https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json)) **[Confirmed]**. The registry label has been "proprietary" since the first commit under that path, before binary releases existed, so it reflects the Agent SDK and Claude Code dependency, not the adapter source. The release archives hold "two files: `claude-agent-acp`, and the Claude CLI (`claude`) it runs" ([adapter README](https://github.com/agentclientprotocol/claude-agent-acp)) **[Confirmed]**. Claude Code's own license is "All rights reserved" with no redistribution grant ([npm LICENSE](https://unpkg.com/@anthropic-ai/claude-code@2.1.322/LICENSE.md)) **[Confirmed]**.

FocusIDE already does the most important thing right: `scripts/fetch-adapter.mjs:73-75` deletes the bundled Claude CLI, and `crates/core/src/acp.rs:240-247` points the adapter at the user's own `claude` through `CLAUDE_CODE_EXECUTABLE`. What remains is the compiled SDK inside the adapter exe. GPL-3.0 is not the problem: the FSF treats programs that talk over pipes as separate programs, and an installer that carries them is an "aggregate" ([GNU GPL FAQ](https://www.gnu.org/licenses/gpl-faq.en.html#MereAggregation)) **[First round]**. The problem is permission to redistribute Anthropic code.

There are three options. **Option A, keep bundling:** agree to Commercial Terms, add a third-party notices file with the Apache license text (none exists today; the repo has only `LICENSE`), state that the exe contains the Claude Agent SDK under Anthropic's Commercial Terms, and fix `README.md:204`. **Option B, download on first use (recommended):** when a user first picks Claude in chat mode, FocusIDE fetches the pinned release from the upstream GitHub URL with a visible prompt, keeps only the adapter, and stores it in app data. Zed already installs `codex-acp` this way ([Zed Codex page](https://zed.dev/acp/agent/codex)) **[First round]**. FocusIDE then does not redistribute Anthropic code, and the installer drops about 113 MB. Option B does not remove the Commercial Terms obligation. It only removes redistribution. The SDK page says its use "is governed by Anthropic's Commercial Terms of Service, including when you use it to power products and services that you make available to your own customers and end users". FocusIDE downloads, launches and drives the SDK-based exe as a core part of chat mode, so the clause most likely still reaches FocusIDE wherever the bytes come from **[Inference]**. The only way to leave Commercial Terms out of chat mode would be to drop Claude chat mode and keep pane mode only. Option B also adds a drift risk: the adapter stays pinned while the user's `claude` updates itself, and the adapter drives that newer binary through `CLAUDE_CODE_EXECUTABLE`. FocusIDE should run `claude --version` at start, record the pair it tested, and show a note when the user's binary is newer than the tested range. **Option C, npm install by the user:** FocusIDE treats the adapter like every other agent on PATH. This needs Node, which the sidecar was chosen to avoid (`PLAN.md:130`). Option B keeps the no-Node setup and removes the redistribution question, so it is the better fit.

## Other vendors: written invitations, one broad Google clause, and one silent OpenAI

### OpenAI Codex

OpenAI has written nothing for or against a third-party app that spawns the user's own Codex with Codex's own login **[Corrected: the first round said "nothing found forbids it"; the accurate statement is that OpenAI is silent, and SIWC is the only written path for a plan in a third-party app]**. Staff statements lean the other way, but they are not terms: secondary sources report that OpenAI's Thibault Sottiaux posted "We are working with OpenCode to allow Codex users to use their Codex subscriptions and usage limits in OpenCode directly" in January 2026 ([falcao.org](https://falcao.org/posts/anthropic-claude-access-crackdown-ecosystem-fallout/)) **[Secondary; the post itself was not fetched]**. That was about token use inside another tool, which is a stronger case than FocusIDE spawning the real `codex`. Codex supports "Sign in with ChatGPT for subscription access" and API keys, and recommends API keys "for automation" ([Codex auth](https://learn.chatgpt.com/docs/auth)) **[Confirmed]**. The adapter moved: `zed-industries/codex-acp` was archived on Jul 22, 2026, and new installs use `@agentclientprotocol/codex-acp`, Apache-2.0, built on app-server ([archived repo](https://github.com/zed-industries/codex-acp), [new repo](https://github.com/agentclientprotocol/codex-acp)) **[Confirmed]**. FocusIDE's install hint still names the archived package (`crates/core/src/agent.rs:208`). The new package "includes a compatible `@openai/codex` dependency", and "To use a different Codex binary, set `CODEX_PATH`" ([new repo](https://github.com/agentclientprotocol/codex-acp)) **[Confirmed]**. So the install hint becomes `npm install -g @agentclientprotocol/codex-acp`, and FocusIDE should set `CODEX_PATH` to the user's own `codex` when one is on PATH, the same way it sets `CLAUDE_CODE_EXECUTABLE`. Then chat mode and pane mode run the same binary and version. The adapter offers ChatGPT login and API key as ACP auth methods; the ChatGPT login is Codex's own browser flow, so FocusIDE can run it in a pane without touching tokens. Codex hooks are "enabled by default" (feature key `hooks`, with `codex_hooks` as a deprecated alias), `UserPromptSubmit` and `Stop` carry a `turn_id`, there is an `Interrupt` event, and "Codex records trust against the hook's current hash" ([Codex hooks](https://learn.chatgpt.com/docs/hooks)) **[Confirmed]**. Pane mode can therefore use the same observe-only hook design as Claude, with the user trusting the hook once in `/hooks`. The same stdout rule applies: on `UserPromptSubmit`, plain stdout "is added as extra developer context". The `Interrupt` event closes a turn that Claude Code would leave open. On Windows the snippet uses the `commandWindows` override. The ChatGPT plan training controls likely apply to Codex content, but that help page was not reachable **[Unverified]**.

### Google: Gemini CLI and Antigravity CLI

Gemini CLI is now an API key and enterprise product. The current ACP flag is `gemini --acp` ([Gemini CLI ACP](https://geminicli.com/docs/cli/acp-mode/)); FocusIDE still passes `--experimental-acp` (`crates/core/src/agent.rs:215`). Antigravity CLI is the consumer path, and it carries the broadest clause of any vendor. Unlisted clients get Gemini models only. Suspension reports name OAuth-plugin token reuse, not the official binary, but an unexplained Nov 8, 2026 appeal mentions Zed's ACP, and official-CLI users report false positives ([forum appeal](https://discuss.ai.google.dev/t/appeal-for-antigravity-account-suspension-for-using-official-zed-gemini-acp/198956)) **[Partly]**. ## Conclusion

The research reframes what FocusIDE's compliance problem is. It is not "which agents may FocusIDE support". Every agent on the list can be supported. The real question is which front end matches which login. API keys fit chat mode everywhere. Subscription logins fit chat mode where the vendor invites third-party clients (GitHub, Cursor, Kiro, Google's ACP page). Where the vendor ties plan billing to its own front end, which today means Anthropic, subscription logins fit pane mode. The biggest surprise is that FocusIDE's current compliance posture for Claude is the riskiest part of the product: it ships Anthropic's proprietary SDK inside its installer and blocks a login method the terms say not to restrict, while the feature it treated as a fallback, the real TUI in a terminal, is the one with written cover.

The design consequence is that pane mode has to be strictly observe-only to keep that cover. Hooks that write files and print nothing, snapshots that read the disk, and summaries built from diffs all add value without putting a single FocusIDE word into the model's context or a single keystroke into the agent. That constraint fits FocusIDE's own principle that "the changes card reads the disk, not the agent's words" (`PLAN.md:86`). Anthropic has changed its billing text twice in five months, and Google's detection is opaque. So written answers from both vendors matter more than any reading of their current pages, and they should arrive before pane mode is marketed to plan users.
